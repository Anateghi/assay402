# HTTP 402 vs 401 vs 403 vs 429: which status code should a paid API return?

The **402 vs 401 vs 403** question matters more for agents than for people. A person reads the error page. An agent branches on the number. If a paid API answers "you have not paid" with 401, a client may look for a missing credential and stop. If it answers "slow down" with 402, a client may sign a second payment for a request that was never going to run. Here is what each code means in the specs, the order Assay applies them, and a client that branches on each one correctly.

```ts
// Branch on the status code before you think about paying (Node 18+, no dependencies).
type Next = "pay" | "retry_later" | "fix_request" | "give_up" | "done";

function nextStep(res: Response): Next {
  switch (res.status) {
    case 200: return "done";
    case 402: return res.headers.has("payment-required") ? "pay" : "give_up"; // x402 v2 challenge
    case 429:
    case 503: return "retry_later";  // honour Retry-After, never re-sign a payment for this
    case 400:
    case 413:
    case 415:
    case 422: return "fix_request";  // paying again will not help
    case 409: return "give_up";      // this payment authorization was already used or is in flight
    case 401:
    case 403:
    case 451: return "give_up";      // not a payment problem
    default:  return res.status >= 500 ? "retry_later" : "give_up";
  }
}

const res = await fetch("{{ORIGIN}}/v1/extract?url=https://example.com/");
console.log(res.status, nextStep(res));                       // 402 pay
console.log(res.headers.get("payment-required")?.slice(0, 40)); // Base64 JSON PaymentRequired
```

## What the specs actually say

**402 Payment Required.** [RFC 9110 §15.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.3) gives it one sentence: "The 402 (Payment Required) status code is reserved for future use." HTTP itself defines no header, body, or retry behaviour for it. The [x402 HTTP transport](https://github.com/coinbase/x402/blob/main/specs/transports-v2/http.md) fills that gap: a 402 carries a `PAYMENT-REQUIRED` header (Base64 JSON with price, asset, network, and `payTo`), the client retries with `PAYMENT-SIGNATURE`, and a paid success carries `PAYMENT-RESPONSE`. The full history is in [What is x402?](/blog/what-is-x402-http-402) and the header details are in [x402 v2 headers](/blog/x402-v2-headers-payment-signature).

**401 Unauthorized.** [RFC 9110 §15.5.2](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.2) says the request "lacks valid authentication credentials" and that a server sending 401 "MUST send a WWW-Authenticate header field" with at least one challenge. That is the key difference from 402. A 401 is about who you are, and it promises an authentication scheme. A pay-per-call API with no accounts has no identity to check, so a 401 has nothing to promise. Assay never returns 401.

**403 Forbidden.** [RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.4): the server "understood the request but refuses to fulfill it", and if credentials were provided, they are "insufficient". A 403 means no amount of payment changes the answer, so it is the wrong code for "please pay." It is the right code for an account ban or a resource you may never read.

**429 Too Many Requests.** [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585#section-4) defines it for rate limiting. The response "MAY include a Retry-After header indicating how long to wait." Rate limits are about time, not money. A gateway that turns "over quota" into a 402 invites clients to pay their way past a limit that is meant to protect the server.

**The rest of the 4xx a paid API needs.** [409 Conflict](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.10) is for a request that conflicts with the current state of the resource. [413 Content Too Large](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.14) and [415 Unsupported Media Type](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.16) describe the request body. [422 Unprocessable Content](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.21) is for content that parses but cannot be processed. [451 Unavailable For Legal Reasons](https://www.rfc-editor.org/rfc/rfc7725#section-3) ([RFC 7725](https://www.rfc-editor.org/rfc/rfc7725)) is for denial "as a consequence of a legal demand."

## How x402 maps its own errors

The x402 HTTP transport spec includes a short mapping table: payment required is 402, a malformed payment payload is 400, a payment that fails verification or settlement is 402, and an internal error during payment processing is 500 ([transport spec, error handling](https://github.com/coinbase/x402/blob/main/specs/transports-v2/http.md)). In practice, check what your server library does. When we sent Assay a `PAYMENT-SIGNATURE` header that was valid Base64 but not JSON, the live gateway answered **402** with a fresh challenge, not 400. A client should treat "402 after I already paid" as "this payment was not accepted", re-read `PAYMENT-REQUIRED`, and stop rather than loop.

## The order matters: check cheap things before asking for money

The status code a client sees depends on the order of checks. Assay runs them in this order (see `src/app.ts` in the [repo](https://github.com/Anateghi/assay402)):

1. **Rate limit and capacity.** A per-IP token bucket (30 requests per minute across `/v1/*`) returns `429` with `Retry-After`. A full concurrency cap on heavy routes returns `503` with `Retry-After: 2`.
2. **Input validation.** A missing or bad URL is `400 invalid_url` or `400 blocked_host`. A wrong body type on `POST /v1/pdf/text` is `415`, and an upload over 10 MB is `413`. These come *before* any payment challenge, so a malformed request never gets a 402 and never costs anything.
3. **Replay guard.** If the same payment authorization is already in flight or has already settled, the answer is `409 payment_replayed`.
4. **Payment.** With no valid payment, the answer is `402` with `PAYMENT-REQUIRED`.
5. **The handler.** Upstream failures and refusals show up here: `451 robots_disallowed` when the target's robots.txt disallows `assay-fetch`, `415` when a page is not HTML or a file is not a PDF, `422` for empty content or an encrypted or corrupt PDF, and `502` when the upstream fetch fails.

You can see the first two steps against the live service with plain `curl`:

```bash
curl -i "{{ORIGIN}}/v1/extract"
# HTTP/2 400
# {"error":"invalid_url","message":"Missing url parameter","charged":false}

curl -i "{{ORIGIN}}/v1/extract?url=https://example.com/"
# HTTP/2 402
# payment-required: eyJ4NDAyVmVyc2lvbiI6Mi...
# {"error":"payment_required","message":"Pay with x402 v2 (exact, USDC on Base Sepolia testnet). Price: $0.003 per successful call.", ...}
```

Step 5 runs after the payment is verified but before it settles. Assay settles only when the handler returns a status below 400, so a `451`, `422`, or `502` from the handler means the authorization was never settled and nothing was charged. Every error body carries `"charged": false` to make that explicit. The full table is in [rate limits and errors](/docs/limits/).

## Why 409 instead of 402 for a replayed payment

A signed x402 authorization is meant to be single-use. The facilitator rejects an EIP-3009 nonce that was already used on-chain, but two identical requests arriving at once could both pass verification before either settles. Assay's replay guard keys each authorization by network, payer, and nonce. A duplicate gets `409` while the first is in flight or after it settled. If the first call failed and was not settled, the nonce is released so the payer can retry with the same authorization.

Returning 402 here would be wrong. It would tell the client to sign a *new* payment for a request that is already being served or was already paid for. A 409 says "this exact attempt conflicts with one we have seen", which matches RFC 9110's wording and tells a well-behaved agent to stop.

## A short decision table

| You want to say | Status | Retry with payment? |
|---|---|---|
| Pay this price, then retry | 402 + `PAYMENT-REQUIRED` | yes |
| Your payment was not accepted | 402 (fresh challenge) | only after fixing the payment, and not in a loop |
| Who are you? (account-based APIs) | 401 + `WWW-Authenticate` | no, authenticate |
| You may never have this | 403 | no |
| Slow down | 429 + `Retry-After` | no, wait |
| Server busy | 503 + `Retry-After` | no, wait |
| Your request is malformed | 400 / 413 / 415 / 422 | no, fix it |
| This payment was already used | 409 | no |
| Legal or policy refusal (for example robots.txt) | 451 | no |

A paid API that keeps these apart lets an agent spend only when spending changes the outcome. Pair it with a client-side budget, covered in [spending limits for agent wallets](/blog/x402-agent-spending-limits), and an agent cannot be talked into paying for a retry storm.

## Where Assay stands today

Assay runs on **Base Sepolia testnet only** (`eip155:84532`) with test USDC, settled through the public x402.org facilitator. Rate limits are in-memory on a single instance, so they reset on deploy. Account-based API keys are not live, which is why there is no 401 path yet.
